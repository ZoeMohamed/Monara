## Current boundaries

The protected [finance layout](../apps/web/src/app/(finance)/layout.tsx) verifies the Supabase identity and loads owned financial records through [backend operations](../apps/web/src/lib/finance/service.ts). The [snapshot adapter](../apps/web/src/lib/finance/presentation.ts) validates transaction/account/category/budget pages and the dashboard, reads every page, and fails if records cannot be loaded completely. Failed loading shows recovery; it never substitutes sample records or partial totals.

The public [demo layout](../apps/web/src/app/demo/layout.tsx) uses the same screens with synthetic session state and no financial API calls. Demo writes and Undo reset on reload. A shared [Demo indicator](../apps/web/src/components/demo-indicator.tsx) labels the active experience once: the mobile space control, mobile Chat header or desktop sidebar. Reset behavior remains available to assistive technology and in the marker's tooltip.

The actual ledger's add/edit/pending-edit/confirm/reject/delete controls call [validated client operations](../apps/web/src/lib/finance/client.ts) through [shared session handling](../apps/web/src/components/use-monara-session.ts), retain drafts on failure, prevent concurrent submits and reload after writes. [Finance synchronization](../apps/web/src/components/use-finance-sync.ts) refreshes selected-month data, ignores stale read results, serializes mutations and blocks writes during loading or recovery. Uncertain results require a successful refresh before another change. Live Undo remains unavailable until a supported durable backend operation exists.

Business writes and verified ownership stay in the Next.js backend. Components hold no provider credentials and do not write financial rows directly to Supabase. Cookie-authenticated finance, Gmail and Chat requests require same-origin checks and return private/no-store responses. The server injects identity; resource UUIDs and disabled controls are not authorization.
