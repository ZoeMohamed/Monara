## Runtime boundary

The protected [layout](../apps/web/src/app/(finance)/layout.tsx) verifies the Supabase session. The [snapshot adapter](../apps/web/src/lib/finance/presentation.ts) validates complete transaction/account/category/budget pages and dashboard output. Failed loading shows recovery. The labelled public [demo](../apps/web/src/app/demo/layout.tsx) uses synthetic memory state and resets on reload.

Financial writes go through [validated client operations](../apps/web/src/lib/finance/client.ts), the Next.js backend and owned repositories. [Synchronization](../apps/web/src/components/use-finance-sync.ts) serializes mutations and rejects stale read results. Creates retain request IDs; edits/review/deletion carry expected versions. Failed drafts remain available; uncertain results block subsequent writes until recovery. Cookie-authenticated mutations require same origin; private responses use no-store. UI contains no provider credentials.

## WhatsApp acceptance blocker

The [webhook](../apps/agent/src/whatsapp/index.ts) resolves a verified link before queueing, but [ConversationSession](../apps/agent/src/whatsapp/session.ts) executes stored messages and retries its outbox without checking the current link. [The Durable Object](../apps/agent/src/whatsapp/conversation.ts) is keyed per User, so relinking a different number retains its history. An offline source reproduction confirmed Agent execution/reply after unlink, a failed reply sent on retry after unlink, and two old-number history turns supplied after relinking. It made **zero external requests**.

Run `node docs/evidence/whatsapp-unlink-audit.mjs` on Node 24 to reproduce the three cases with synthetic repositories/transports and no network requests. The [diagnostic](evidence/whatsapp-unlink-audit.mjs) asserts the current unsafe behavior; its successful run is not acceptance.

Argya owns the fix: bind queued work, outbox and history to a verified link generation; revoke stale work/history and revalidate each backend operation and outbound send. This is an actual F12/ER9 blocker, not a completed safety check. UI status recovery and a successful unlink response do not resolve it.

## Local Gmail acceptance

Run `pnpm dev`, `pnpm dev:tunnel` and `pnpm dev:agent` separately. ngrok's inspector is not the app. Local credentials belong to the development Composio project only. Start Gmail consent from the configured public HTTPS app origin after signing in there. The [callback helper](../apps/web/src/lib/gmail/callback.ts) validates that origin; forwarded headers do not establish trust.

The project owner must configure Composio's verifier at that origin plus `/api/gmail/connections/callback` and allow the same origin plus `/auth/callback` in Supabase. See [Composio callback settings](https://docs.composio.dev/reference/api-reference/connected-accounts) and [Supabase redirects](https://supabase.com/docs/guides/auth/redirect-urls). Test reconnect and disconnect, first import, queue recovery, repeat imports and rejected items separately. This handoff does not authorize provider settings, deployment, remote migrations or external messages.
