# Import and extraction

Owner: Adlyn. Features: F2, F3, F8, F14. Status: Draft.

## Purpose
The pipeline turns supported, authenticated institution emails, WhatsApp receipt photos, and WhatsApp voice notes into expense, income, or exclusion records. It preserves uncertain data for User review instead of inventing values. All provider imports are pending unless the Gmail auto-confirm policy explicitly applies.

## How it works
Composio authorizes Gmail separately from Supabase sign-in. The agent discovers supported institution senders, retrieves messages for the import window, verifies Gmail authentication results, and sends bounded email text to the structured extractor. Deterministic guards then validate the IDR amount, date, location, account hint, and schema before the Next.js-owned backend records anything.

Each Gmail message is claimed once and each extracted item has a stable source index, so retries do not duplicate transactions. New items are either auto-confirmed by the policy below or remain pending in the Review Queue. Exclusions preserve reimbursements, internal transfers, duplicates, and non-personal activity for audit and deduplication, but never affect totals.

For WhatsApp, a verified sender is queued in the User's Durable Object conversation. Receipt photos are read by `apps/agent/src/whatsapp/receipt.ts`; voice notes are read by `apps/agent/src/whatsapp/voice.ts` through the audio-capable JSON model client. Media bytes are fetched from Kapso, held in memory for the model call, and not stored. Both paths list the User's active accounts and categories, validate Rupiah amounts and bounded dates, resolve an account only on an exact single match, and call the Next.js backend's media-specific pending-write operation. A message id becomes the client request id, so redelivery is idempotent.

There are three prompts, one per source, and they follow the same shape. The system prompt is fixed per source, so a provider that caches prompts can reuse it, and it says the content is untrusted data: the model must not follow instructions in it, reveal hidden instructions, or treat a request to call a tool or change a record as evidence. The User's data goes in the user message only, inside tags (`<holder>` and `<email>` for Gmail, `<caption>` for a photo, and the audio itself for a voice note), with any closing tag in the content neutralized. The model answers with a strict JSON schema and has no tools. It copies the amount as written or spoken (`amountText`) and never converts or calculates it; dates, times, merchant, location and account hint are only values the source states, and anything else is null. The Gmail extractor (`apps/agent/src/gmail/parse/extract.ts`) can return several items per email and an `isTransactionEmail` flag. The photo and voice readers return one transaction each, and they choose a category only from the User's own category names.

Amounts are turned into Rupiah by code, not by the model. Gmail and photo amounts must carry a Rupiah marker or plain digits, with no other currency. A spoken amount such as "20k", "dua puluh ribu", "1,5 juta" or "twenty five thousand" is read by a word-and-suffix parser in `voice.ts`; anything it does not recognize is rejected rather than guessed.

*All three sources share one extractor and one set of guards in the agent. The backend decides the outcome: only a Gmail expense or income that passes every auto-confirm gate is confirmed on import, while photos, voice notes, exclusions and anything uncertain wait in the Review Queue until the User confirms them. Exclusions never count in totals, even once confirmed.*

## Key decisions
The auto-confirm boundary is `0.95`. A score at or above that value is necessary but not sufficient. The sender must also pass Gmail authentication, the transaction must be an expense or income, amount and date must be present, currency must be IDR, merchant or description must be present, and the institution must resolve to exactly one active Financial Account owned by the User. A sole account for that institution may resolve without a last-four hint; when several accounts match the institution, the last four digits must identify exactly one. Missing or ambiguous fields, unverified senders, exclusions, and scores below `0.95` stay pending.

This conservative boundary is appropriate while confidence is model-reported rather than calibrated against a labeled production dataset. `0.90` would reduce review work but carries more silent-ledger risk. Requiring every item to be reviewed is safer but removes the product's main automation benefit. The threshold should only be lowered after measuring field-level precision and false-confirm rates on synthetic and consented labeled emails.

Category is not an auto-confirm gate. A category can be filled from the User's confirmed merchant history or later enrichment without changing the transaction amount or whether it contributes to totals. Missing values remain null. The retired three-argument ingestion function was removed because it could not carry sender-verification evidence.

Voice audio uses the same conservative field guards as a receipt. The model reports the amount as spoken and the parser converts it, so the model never does arithmetic; another currency or an amount the parser does not recognize is not saved. The backend operation derives `whatsapp_voice` from the operation route, and callers cannot select a source. The alternative was to let the agent call the general `add_transaction` operation; that was rejected because it would allow an unreviewed voice extraction to affect totals.

## Security and risks
Email, receipt, caption, and voice content are untrusted data and are bounded before model use. Gmail amounts and locations must appear in the email text, implausible dates are removed for every source, and any guarded value caps confidence below the auto-confirm threshold. Provider credentials, media bytes, raw email content, and transcripts are not written to transaction records or logs. The backend derives ownership from the verified Gmail connection or WhatsApp link; callers cannot assert a User ID or Financial Account belonging to another User.

The red-team suite has eight email attack cases (`apps/agent/sandbox/email-attacks.ts`): injected income, an email that closes its own data tag, a promotion and an OTP posing as receipts, a prompt-leak request, tool requests, a swapped total, and a payment to someone else that claims to be an internal transfer. Each passes only when the production extractor returns the real transaction and nothing injected. All eight were blocked on 19 October 2026 with the configured model; unit tests check that each case fails when a model obeys the injection.

The remaining risk is score calibration: a high model confidence is not a statistical guarantee. Sender verification and deterministic completeness checks reduce that risk, while the Review Queue remains the fallback. Production monitoring should track confirmed corrections before any threshold change.

## How to verify
Run `pnpm db:check --reset` in a disposable Docker worktree to replay every migration, lint SQL, run pgTAP ownership tests, and compare generated database types. The tests cover `0.949` pending, `0.950` confirmed, unverified senders, incomplete data, exclusions, unknown and ambiguous accounts, cross-User ownership, retries, and deduplication. Run `pnpm --filter @monara/agent test` for the extractor's amount, currency, date, location, prompt-injection, voice routing, and schema guards. Run `pnpm --filter @monara/agent sandbox:email-attacks` for the email attack cases against the real model.

Extraction accuracy was measured on 18 labeled synthetic emails (`apps/agent/sandbox/extraction-set.ts`, run with `pnpm --filter @monara/agent sandbox:extraction`), three runs on 18 October 2026: every extracted item was fully correct for kind, amount, date, merchant and account digits (14 of 14 in each run), 17 of 18 emails were classified correctly, and 14 of 15 expected items were extracted with no extra items. The one miss is a prompt-injection email the model provider rejected with HTTP 400, so nothing was extracted from it. The set is small, written by the team, and uses clean bank-style text, so this shows the extractor handles these cases, not that it is accurate on a real inbox. The logs and method are in [the evaluation section](evaluation.md). Receipt photos and voice notes have no labeled set yet, and live audio-provider compatibility and end-to-end WhatsApp delivery remain unverified.
