# Import and extraction

Owner: Adlyn. Features: F2, F3, F8, F14. Status: Draft.

## Purpose
The pipeline turns supported institution emails and WhatsApp receipt photos into expense, income, or exclusion records. It preserves uncertain data for User review instead of inventing values. Receipt photos always wait for review; a Gmail import is confirmed only when the review policy below explicitly applies. Voice notes are not part of this release.

## How it works
Composio authorizes Gmail separately from Supabase sign-in. The agent reads only the exact senders for the User's active accounts, from `packages/contracts/src/institutions/institution-senders.json` or the User's own Custom Banks. It retrieves messages for the import window, records whether Gmail authenticated the sender (`apps/agent/src/gmail/sender.ts`), and sends bounded email text to the structured extractor. Deterministic guards then validate the IDR amount, date, location, account hint, and schema before the Next.js-owned backend records anything.

Each Gmail message is claimed once and each extracted item has a stable source index, so retries do not duplicate transactions. After import, `apps/agent/src/merchant/categorize.ts` picks a Category of the matching type with its own confidence score, and the backend settles the item as confirmed or pending in the Review Queue. Exclusions preserve reimbursements, internal transfers, duplicates, and non-personal activity for audit and deduplication, but never affect totals.

For WhatsApp, a verified sender is queued in the User's Durable Object conversation. Receipt photos are read by `apps/agent/src/whatsapp/receipt.ts`. The photo bytes are fetched from Kapso, held in memory for the model call, and not stored. The reader lists the User's active accounts and categories, validates the Rupiah amount and a bounded date, resolves an account only on an exact single match, and calls the backend's `add_receipt_transaction` operation. The WhatsApp message id becomes the client request id, so redelivery is idempotent.

There are two prompts, one per source, and they follow the same shape. The system prompt says the content is untrusted data: the model must not follow instructions in it, reveal hidden instructions, or treat a request to call a tool or change a record as evidence. The User's data goes in the user message inside tags (`<holder>` and `<email>` for Gmail, `<caption>` for a photo's caption), with any closing tag in the content neutralized. The model answers with a strict JSON schema and has no tools. It copies the amount as written (`amountText`) and never converts or calculates it; dates, times, merchant, location and account hint are only values the source states, and anything else is null. The Gmail extractor (`apps/agent/src/gmail/parse/extract.ts`) can return several items per email and an `isTransactionEmail` flag. The photo reader returns one transaction and chooses a category only from the User's own category names.

Amounts are turned into Rupiah by code, not by the model. They must carry a Rupiah marker or plain digits, with no other currency, and a Gmail amount must appear in the email text. Anything the parser does not recognize is rejected rather than guessed.

Exclusions never count in totals, even once confirmed.*

## Key decisions
A Gmail import is confirmed when its Review Confidence, the lower of the extraction and categorization scores, is at least `public.gmail_auto_confirm_confidence()` (`0.5`). When only one score is known it is used alone; with neither, the item stays pending. The score is necessary but not sufficient: the item must also map to exactly one active Financial Account owned by the User, have an amount in IDR, a date, a known cash direction, and a Category whose type matches the transaction. A sole account for an institution may resolve without a last-four hint; when several match, the last four digits must identify exactly one. The policy is in `supabase/migrations/20261019160000_gmail_confidence_only_review.sql`.

Taking the lower of the two scores means a confident amount cannot carry an uncertain category into the ledger, or the reverse. The earlier policy confirmed only at `0.95` on the extraction score and also required Gmail sender authentication. That was safer, but it sent more complete imports to the Review Queue. Sender authentication is still recorded as evidence but no longer adds a review gate; the narrower defence is that only the User's listed senders are read at all. The cutoff remains model-reported rather than calibrated, and should only change after measuring false-confirm rates on labeled emails.

An email with no usable date, or a date beyond belief, takes the day the email arrived in Asia/Jakarta. That is a fallback the email supports, not an invented date, and it does not by itself send the item to review. An unstated cash direction is never invented: the item falls back to Expense Misc and stays pending. Internal, the only exclusion recognized automatically, requires the counterparty name to match the User's confirmed profile name deterministically (`private.holder_name_matches`); a model label alone is not enough.

Receipt photos never auto-confirm. The backend operation derives `whatsapp_receipt` from its route, and callers cannot select a source. The alternative was to let the agent call the general `add_transaction` operation; that was rejected because it would allow an unreviewed photo extraction to affect totals. Voice-note extraction was built and tested in a separate branch but is not part of this release.

## Security and risks
Email, receipt, and caption content are untrusted data and are bounded before model use. Gmail amounts and locations must appear in the email text, implausible dates are replaced or removed, and a guarded field caps extraction confidence at `0.5`. Provider credentials, photo bytes, and raw email content are not written to transaction records or logs. The backend derives ownership from the verified Gmail connection or WhatsApp link; callers cannot assert a User ID or Financial Account belonging to another User.

The red-team suite has eight email attack cases (`apps/agent/sandbox/email-attacks.ts`): injected income, an email that closes its own data tag, a promotion and an OTP posing as receipts, a prompt-leak request, tool requests, a swapped total, and a payment to someone else that claims to be an internal transfer. Each passes only when the production extractor returns the real transaction and nothing injected. All eight were blocked on 19 October 2026 with the configured model; unit tests check that each case fails when a model obeys the injection.

The main remaining risk is score calibration: the `0.5` cutoff is low, and a model score is not a statistical guarantee. The guard cap equals the cutoff, so a guarded location or date lowers confidence without holding the item back on its own; a guarded amount does hold it, because the amount is removed. Completeness checks, account ownership, and the minimum of two scores reduce the risk, while the Review Queue remains the fallback. Production monitoring should track User corrections to confirmed imports before any threshold change.

## How to verify
Run `pnpm db:check --reset` in a disposable Docker worktree to replay every migration, lint SQL, run pgTAP ownership tests, and compare generated database types. `supabase/tests/database/gmail_confidence_review_ownership.test.sql` covers the `0.5` cutoff, `0.49` scores on either side, missing scores, rounding at `.4995`, sender authentication adding no gate, missing amount, direction or account, Internal and Person priority, deactivated accounts, wrong-typed or archived categories, and User edits surviving background classification. Run `pnpm --filter @monara/agent test` for the extractor's amount, currency, date, location, prompt-injection, receipt, and schema guards. Run `pnpm --filter @monara/agent sandbox:email-attacks` for the email attack cases against the real model.

Extraction accuracy on a labeled email set is not yet measured in this repository; the Evaluation section owns that metric. Receipt photos also have no labeled set, and end-to-end WhatsApp delivery remains unverified.
