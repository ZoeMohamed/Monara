## Why this run exists and how it differs from the baseline

The 18 October baseline ran on `00700cd`. Production now runs `cce75b9`, which adds, among other changes, typed Gmail categorization (#76), faster onboarding and internal-transfer matching (#87), the new extractor and confidence policy (#89), per-User rate limits (#62), permanent User deletion (#67) and the spending forecast (#63). The Agent tool catalog also grew: `get_dashboard`, `list_reminders`, `get_spending_forecast` and `refresh_spending_forecast` are now registered.

The Sandbox scenarios and the extraction email set are unchanged since the baseline. The only harness change is one line in `apps/agent/sandbox/ledger.ts` (#76), which gives the synthetic Categories a Transaction Type. The same model label was used. Results are therefore a separate series on newer code with the same suite, and they are not merged into the baseline totals.

## Forecast backtest (rules only)

`packages/core/src/forecast.test.mjs`, "backtest on synthetic history", passes in the core suite above. It forecasts from a constructed history with a cutoff of 1 October 2026 and compares with a constructed October in which Netflix was cancelled, one chicken-rice day was skipped, Spotify cost more and a new subscription started. Result: 16 predictions due, 14 realized, mean absolute amount error 5.2% among the 14. The two misses are the cancelled Netflix and the skipped day. The forecast was built with no model judgments, so this says nothing about whether the optional model refinement helps, and the history is not real spending.

## What this evidence does not show

- A signed-in User on the real backend. The Sandbox ledger is in memory, so Supabase RLS, ownership checks and concurrency are not exercised here; they are covered by the CI database job.
- Real mailboxes, receipt photos or voice notes, the WhatsApp channel end to end, or flooding.
- The auto-confirm rule. Production now confirms a Gmail import when the lower of the extraction and Category scores is at least 0.5, with no sender-authentication gate. No false auto-confirm rate has been measured.
- General safety. A pass shows the Agent held in these cases with this model, not that it always will.

## Open decisions

- **`bills-due` expectation.** Decide whether the scenario should now expect the Agent to list bills from `list_reminders`. Keep this run's result as recorded, and define any revised suite separately.
- **`no-date-stated` label.** After this run, #94 restored the received-date fallback in the extractor (`statedDate ?? receivedOn(email.receivedAt)` on `c9e5ea0`), so the original label matches current `main` again. This run's result stays as recorded for `cce75b9`; a rerun on the current commit would confirm it.
- **Provider instability.** Decide whether to repeat the full series when the provider is stable. Failed runs stay in the record either way.
- **Extraction harness location.** It exists only on the submission branch, so `main` cannot reproduce the extraction measurement until #85 merges.
- **Security assessment.** PR #90 describes the 0.95 auto-confirm rule of `e6a70e8`. Production now uses 0.5 without a sender gate, so the assessment needs updating once the submission branch takes `main`.
