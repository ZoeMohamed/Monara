# Meeting UI handoff, 17 October 2026

Accepted scope for this change: complete the UI and necessary browser-safe contracts on top of main. Main owns the stored ledger model (expense, income and exclusion; pending and confirmed), Gmail auto-confirmation, server-reported sync status and first-run onboarding; this UI follows it wherever the two overlap. Provider configuration, external delivery and deployment are outside this UI change.

## Ledger and categories

The UI uses the stored types expense, income and exclusion. Exclusions stay visible in History with a muted appearance and never contribute to spending, income, budgets or daily/weekly guides. As in the backend, an exclusion may omit its amount, date and account; anything entered must still be valid. Excluding a pending import (formerly Reject) confirms it as an exclusion, which keeps it for audit and offers Undo in the demo.

History is one dated list containing confirmed and pending records. All, Expenses, Income, Exclusions and To review share one filter row. Pending rows have a subtle highlight and one quick confirm/edit action, with no review tags; details retain edit, confirm and exclude. Missing dates remain visible under Date needed and require the actual date before confirmation. Confidence is never displayed.

The [preset catalog](../packages/contracts/src/category-presets.ts) contains Aiccountant's 19 shipped expense slugs and the six supplied exclusion reasons: Repayment, Internal, Reimbursed, Investment, One-off and Cancelled. Each has a drawn icon. Reference: the public [Aiccountant dashboard](https://dashboard.aiccountant.id/) client catalog inspected on 17 October; labels unavailable without authentication use readable slug expansions. The catalog is a UI integration contract, not a database seed. Live selectors use owned persisted category/account UUIDs and offer only reasons for exclusions and only spending categories otherwise; the reason is optional, and an excluded import may keep the category it was imported with.

Backend follow-up:

- Done on main: the stored transfer kind is replaced by exclusion, review is pending/confirmed, high-confidence Gmail imports confirm automatically, and `profiles.full_name` is stored for recognising a User's own transfers.
- Still open: seed the preset categories (expense and exclusion reasons) idempotently for existing and new Users, with a durable expense/exclusion classification rather than inferring it from display labels. Until then, live exclusions save without a reason.
- Automatic categorization may choose any expense preset and only Internal from the exclusions. Compare the verified User's name with the extracted transfer/payment recipient; expose a concise categorization reason when supported by source evidence. Name similarity is a classification signal, not authorization or proof that an account belongs to the User. Other exclusion reasons require an explicit User decision.
- Apply a configurable confidence threshold only after required amount, currency, actual transaction date and account association are valid. High-confidence records may be confirmed automatically; incomplete/uncertain records still need review. The meeting did not specify a numeric threshold.
- Resolve actual transaction dates from source evidence. Do not substitute the polling/import date or manufacture amounts or account mappings.

## Weekly gauge

Home includes a weekly arc gauge and seven daily spending bars. Matching weekly budget periods use their actual limits and budgeted-category expenses. Monthly-only setups show an explicitly labelled weekly guide allocated from the relevant monthly periods. Different weekly reset days do not imply one shared weekly limit. Pending records, income and exclusions never count. Historical months do not present the current week as historical activity.

## Gmail and onboarding

Gmail checks run automatically every 15 minutes (the Agent's scheduled worker), so the Gmail screen has no manual sync button; it shows that cadence, the server-reported sync state, reconnect/disconnect and account suggestions. Onboarding is main's first-run bottom sheet on Home (Gmail consent, bank detection, full name, import progress), with its Connect step illustrated by Gmail's four-colour mark on an app tile. This branch's separate `/onboarding` page was dropped in favour of it.

Main already polls a rolling 30-day window, maps senders to institutions and accounts, and backfills newly added accounts. Still open for Adlyn's workflow: fan eligible emails into concurrent durable extraction jobs. Durable dedupe must prevent the same User/mailbox/message identity from being extracted or inserted twice, including retries and concurrent jobs. A newly added Financial Account must become eligible for the next poll's 30-day backfill even when other accounts already completed earlier scans. Detect available bank accounts before transaction processing and resolve to owned persisted UUIDs. Keep provider extraction, merchant enrichment and category reasoning behind the established Agent/backend boundary. Merchant search results are untrusted input and cannot authorize writes.

## Chat and reminders

Chat history UI retains separate conversations in the current mounted app session, including navigation and New chat. Durable history across reloads/devices requires owned backend storage and pagination. Do not cache financial chat records in the service worker. Restoring an old conversation must not revive destructive-action confirmation authority.

Receipt UI and media contracts prepare image selection, preview/removal, image-only transaction intent and visual response display. The backend must validate uploads, store them privately in Supabase Storage with ownership policies, use expiring access URLs, and extract expense/income/exclusion using the shared presets. An image sent without text defaults to transaction import. Until that operation exists, the UI cannot report that a transaction was imported. Summary/visual prompts use the existing chat bridge; summary tools, app-themed generated visual images and receipt extraction remain Agent integrations. Model copy should be casual and natural, without em dashes.

Proactive WhatsApp budget reminders are supported by the provider. Kapso accepts outbound template messages through `POST /{phone-number-id}/messages`; a budget alert should use a Meta-approved template with its registered language and body parameters. Free-form text is allowed only within 24 hours of the latest inbound User message; outside that window an approved template is required. Obtain explicit reminder opt-in, check the verified WhatsApp Link and preferences before each send, and honor opt-out. These requirements were checked on 17 October against [Kapso’s Cloud API guide](https://kapso.com/whatsapp-cloud-api) and the [WhatsApp Business Messaging Policy](https://business.whatsapp.com/policy).

Monara already has `WhatsAppTransport.sendTemplate`, confirmed-expense threshold reminder creation at the configured warning percentage and 100%, a reminder dedupe key, and `reminder_deliveries` storage. Production dispatch is still missing: the scheduled worker currently handles Gmail only, and no runtime caller sends reminder templates. The current link repository retains a phone HMAC and last four digits, which cannot reconstruct an outbound recipient; a verified provider contact/delivery route must be resolved server-side. Adlyn’s follow-up connects an authenticated durable dispatcher, owned recipient resolution, persisted opt-in, one delivery per reminder/channel with retry handling, and provider status updates. The contract’s `budget_alert` name does not establish that Meta approved a template. A provider message ID records acceptance, not confirmed delivery. No external send was performed in this UI change.

## Verification boundary

Core actions now state their outcome and next step. Confirming, adding and editing transactions offer Undo using the existing owned backend action receipt; demo confirm/reject/add/edit/delete reversals restore only the affected record and refuse to overwrite later changes. Live delete/reject confirmation states when Undo is unavailable. Warning messages remain visible until dismissed or resolved and offer Refresh or History instead of a success checkmark.

An uncertain create retains its request identity, original values and draft even after closing and reopening the editor. It cannot be resent with a changed body. Existing-record edits retain their reviewed version; refreshed conflicting values require comparison and an explicit choice before saving. Inactive accounts and archived categories are caught before submission. Drafts warn before closing or leaving the page, and financial/chat content is not written to browser storage. Budget updates provide outcome/Undo, stale budgets require review of their refreshed settings, and removed budgets preserve draft recovery. Uncertain chat replies require checking History before resending; unsent text and photos remain with their conversation within the mounted app session.

Failure verification includes offline preflight, response loss after a simulated committed write, concurrent taps, stale reads, failed refresh, changed-record conflict, expired/consumed Undo receipts, receipt ownership, zero/invalid budget limits, duplicate categories, unavailable image import and retained drafts. The uncertain-create regression produces one simulated physical write across retries. These are local simulations and browser checks, not evidence of configured live providers or a guarantee against every possible failure.

Mobile UI checks use 390 × 844 CSS pixels. Automated contract/ledger tests establish arithmetic, validation and boundary behavior. Builds establish source compatibility; they do not establish provider configuration, completed cloud migrations, Gmail ingestion, stored chat/media or WhatsApp delivery.
